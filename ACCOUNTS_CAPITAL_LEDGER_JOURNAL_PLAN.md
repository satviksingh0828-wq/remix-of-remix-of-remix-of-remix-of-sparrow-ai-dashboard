# Accounts Capital Ledger and Journal Plan

## 1. Objective

The Accounts module will be extended with a branch-specific capital-ledger workflow and a Journal module. The design will preserve double-entry accounting at the database boundary, make opening balances auditable, and provide consistent Master/Ledger-style navigation on mobile and desktop.

The requested outcome is:

1. Every branch has one system-generated default capital ledger.
2. Capital ledgers appear as a distinct Ledger sub-tab.
3. Only capital ledgers accept manually entered opening balances.
4. Revenue ledgers do not expose or accept opening-balance fields.
5. Bank and cash masters remain ledger accounts and create automatic opening-balance journal entries.
6. Journal users can create entries containing multiple debit and credit lines across capital, bank, cash, and other permitted ledger accounts.
7. Every journal entry must balance before it can be saved.
8. The Journal module has Create and List sub-tabs, filters, Excel import/export, and per-entry PDF export using the existing branded PDF header.

### Existing database capabilities

The current schema already models `ledger_accounts` with `ledger_type` values of `revenue`, `capital`, `bank`, and `cash`. It also links system bank and cash ledger records back to their source master records. Bank and cash triggers attempt to create automatic opening journal entries.

### Current gaps requiring correction

The existing schema is only a partial foundation for the requested behavior.

1. `create_manual_ledger` accepts both `revenue` and `capital` and accepts opening-balance parameters for both. This conflicts with the requirement that revenue ledgers cannot have opening balances.
2. The current Ledger UI exposes opening-balance fields while creating revenue ledgers.
3. There is no guaranteed one-per-branch default capital ledger.
4. The current opening-balance offset line is not linked to a real ledger account. It is inserted with only `account_kind = 'ledger'`, which is not sufficient for a complete, traceable double-entry posting.
5. There is no database function that atomically validates and posts a manual journal with multiple lines.
6. The current `journal_lines` table checks that each line is either debit or credit, but it does not enforce that a journal entry has at least two lines or that total debits equal total credits.
7. Bank and cash opening entries are generated by triggers, but the posting behavior must be revised so the opposite side is a real branch-level offset ledger and all generated entries remain idempotent.
8. There is no Journal route, Journal page, journal create form, journal list, filter state, Excel import/export flow, or journal-entry PDF view.
9. Existing row-level security policies are open to `anon` and `authenticated`. This is already the project pattern for these Accounts tables, but the new RPCs must still perform all accounting validation server-side.

## 3. Accounting Model

### 3.1 Account classes

Each branch will have the following relevant account classes:

| Account class | Source | Can be manually created? | Opening balance allowed? | Journal posting allowed? |
|---|---|---:|---:|---:|
| Capital | One system capital ledger per branch | No, system-created | Yes | Yes |
| Revenue | Manual ledger | Yes | No | Yes, subject to permission and account rules |
| Bank | Bank Master record, auto-synced | Through Bank Master only | Yes, through Bank Master | Yes |
| Cash | Cash Master record, auto-synced | Through Cash Master only | Yes, through Cash Master | Yes |
| Opening Balance Equity | One system offset ledger per branch | No, system-created | No direct user opening balance | Used automatically for opening-balance balancing |

The phrase “capital ledger” will mean the system-generated capital account for a branch. The account name may be displayed as `Capital - <Branch Name>` while remaining internally stable through a system flag and branch constraint.

### 3.2 Branch isolation

Every ledger account, journal header, and journal line will carry a branch. A journal entry will be branch-scoped, and every selected line account must belong to the same branch as the journal header. The UI will filter selectable accounts by the selected branch and will reject cross-branch lines in the database function.

### 3.3 Opening-balance accounting

Opening balances will be posted as complete journal entries, not as values that exist only on master rows.

For a capital opening balance:

| Debit | Credit |
|---|---|
| Opening Balance Equity, when the capital balance is credit-natured | Branch Capital Ledger |
| Branch Capital Ledger, when the capital balance is debit-natured | Opening Balance Equity |

For a bank or cash opening balance:

| Debit | Credit |
|---|---|
| Bank or Cash Ledger | Opening Balance Equity |

The opening-balance entry will have `source_module = 'auto'`, a stable reference such as `account_opening:capital:<branch_id>` or `account_opening:bank:<master_id>`, and status `approved` only after the complete balanced transaction has been created.

The system will use one real `Opening Balance Equity` ledger per branch. This prevents orphan offset lines and makes the opposite side visible in journal details and ledger statements.

### 3.4 Journal balancing rule

A journal is valid only when:

```text
sum(debit lines) = sum(credit lines)
```

The total must be greater than zero. Every line must have exactly one of debit or credit greater than zero. At least two lines are required. Amounts are stored at two decimal places and validated as finite, non-negative numeric values.

## 4. Proposed Database Changes

A new migration will be added after the existing Accounts migrations. It will be written to be safe to run repeatedly and will include verification queries.

### 4.1 Ledger account constraints and metadata

The migration will add or normalize:

- `is_default_capital boolean not null default false`.
- `is_opening_offset boolean not null default false`.
- A stable system account code, for example `system_code text`, to identify `CAPITAL` and `OPENING_BALANCE_EQUITY` per branch without relying on display names.
- A unique partial index enforcing one default capital ledger per branch.
- A unique partial index enforcing one opening-balance-equity ledger per branch.
- A constraint preventing `revenue` ledgers from carrying an opening balance or opening-balance date.
- A constraint that system bank/cash ledger rows remain linked to their source master.

The exact constraint will be compatible with the existing migration history. If an existing database contains invalid revenue opening values, the migration will first normalize those values to zero and clear their opening dates before adding the constraint.

### 4.2 Capital and offset account provisioning

A provisioning function will create missing system accounts for every existing branch and will be called again from the branch-provisioning path if one exists. It will:

1. Create `Capital - <Branch Name>` when no default capital ledger exists.
2. Create `Opening Balance Equity - <Branch Name>` when no offset ledger exists.
3. Mark both records as system accounts and inactive only if their branch is inactive according to the project’s branch model.
4. Never create duplicates if called multiple times.

The function will be idempotent and protected by the partial unique indexes.

### 4.3 Manual ledger RPC

The existing `create_manual_ledger` function will be replaced or versioned with a function that accepts only the fields appropriate to the selected type.

For `capital`, the user will select the branch and enter an optional opening balance, date, and side. The function will create or return the branch default capital ledger and create the balanced opening entry when the amount is non-zero.

For `revenue`, the function will accept branch and description only. It will reject any opening-balance amount or date supplied by a client.

The UI may hide fields, but the database function remains the final enforcement point.

### 4.4 Automatic bank and cash opening postings

The existing bank and cash sync functions will be corrected to:

- Resolve the branch’s real Opening Balance Equity ledger.
- Create two complete journal lines, both linked to valid ledger accounts.
- Delete and recreate only the matching auto-generated entry when a source opening balance changes.
- Avoid creating an entry for a zero amount or missing opening date.
- Preserve a stable reference for idempotence.
- Keep the source bank/cash ledger’s opening balance synchronized with its master record.

### 4.5 Manual journal posting RPC

A new security-definer function will accept a JSON payload containing:

- Branch ID.
- Entry date.
- Header description.
- Optional reference.
- A list of journal lines.

The function will perform all validation and insertion inside one transaction. It will:

1. Validate that the branch exists.
2. Validate that the description and date are present.
3. Validate that at least two lines exist.
4. Validate that every amount is positive and has only one side populated.
5. Validate that every selected ledger belongs to the chosen branch and is active.
6. Resolve bank/cash source identifiers through the linked `ledger_accounts` row rather than trusting client-supplied account kinds.
7. Validate equal debit and credit totals.
8. Generate a unique voucher number.
9. Insert the journal header and all lines.
10. Return the created entry with its voucher number.

No partially inserted journal will remain if any validation fails.

### 4.6 Journal read and export queries

The migration will add indexes for:

- Branch and entry date.
- Voucher number.
- Source module and reference.
- Journal lines by ledger account.

The application will read journal headers and lines in separate, explicit queries or through a stable view. A view may be added for list display if it improves consistent filtering and aggregate totals.

## 5. Ledger UI Plan

### 5.1 Ledger sub-tabs

The existing Ledger navigation will become:

1. **Capital**
2. **Create**
3. **List**
4. **View**

The mobile navigation will use the same shared TMS `MobileTabDropdown` component already used by Operations. The desktop sidebar will use the same visual language as the existing Master and Ledger navigation.

### 5.2 Capital tab

The Capital tab will show the selected branch’s default capital ledger and its current balance summary. It will provide:

- Branch selector.
- Capital ledger name and system status.
- Opening balance amount.
- Opening balance date.
- Opening balance side, debit or credit.
- Save/update action.
- Opening-balance journal reference and link to the Journal list/detail view.
- A clear statement that the opposite side is posted automatically to the branch Opening Balance Equity ledger.

The Capital tab will not allow creation of a second capital ledger for the same branch.

### 5.3 Create tab

The Create tab will retain manual revenue-ledger creation but will no longer show opening-balance fields for revenue.

It will include:

- Branch.
- Ledger description/name.
- Ledger type fixed to Revenue for the manual form.
- Save action.

If the product requires manual capital creation in the future, it will not create a second capital account. The Capital tab will remain the only place to maintain the branch capital ledger.

### 5.4 List tab

The existing list will be updated to:

- Display Capital, Revenue, Bank, and Cash type badges.
- Mark system accounts and default capital accounts clearly.
- Show branch, opening balance status, and current calculated balance where available.
- Prevent direct deletion of system capital, opening-equity, bank, and cash ledger rows.
- Keep filters for branch, ledger type, and search.

### 5.5 View tab

The View tab will show the selected ledger’s statement from journal lines. It will include:

- Branch selector.
- Ledger selector.
- Date range.
- Opening balance.
- Debit total.
- Credit total.
- Closing balance.
- Voucher number, date, description, reference, and opposite account for each posting.

## 6. New Journal Module Plan

### 6.1 Navigation and routes

A new Accounts module route will be added at `/accounts/journal`, with a new page component such as `AccountsJournalPage.tsx`. The Accounts section navigation will include Journal alongside Masters and Ledger.

Journal will have two sub-tabs:

1. **Create**
2. **List**

The mobile sub-tab control will be the exact shared `MobileTabDropdown` used by TMS Operation sub-tabs and the updated Accounts navigation.

### 6.2 Journal Create tab

The form will include:

- Branch selector.
- Entry date.
- Header description.
- Optional reference or voucher note.
- A dynamic line grid.

Each line will contain:

- Account selector.
- Debit amount.
- Credit amount.
- Line description.
- Optional display of account type and source, such as Capital, Bank, or Cash.

The user will be able to add multiple lines and remove lines. The account selector will include the branch’s active Capital, Revenue, Bank, and Cash ledgers. Bank and cash accounts will be treated as ledgers in the same selector and will not need a separate posting workflow.

The form will show live totals:

| Summary | Behavior |
|---|---|
| Total debit | Sum of all debit lines. |
| Total credit | Sum of all credit lines. |
| Difference | Debit minus credit. |
| Status | Balanced or Not balanced. |

The Save button will remain disabled until the entry is balanced and otherwise valid. The server RPC will repeat the validation so the accounting rule cannot be bypassed.

### 6.3 Journal List tab

The list will display:

- Voucher number.
- Entry date.
- Branch.
- Description.
- Source, such as Manual or Auto.
- Debit total.
- Credit total.
- Balance status.
- Created time.
- Actions for View, Export PDF, and, where allowed, Edit or Reverse.

The default list will include both manual journal entries and automatic opening-balance entries. Automatic entries will be visually labeled and will not be editable from the manual Journal form.

### 6.4 Filters

The Journal list will support:

- Branch.
- Month, implemented as a month picker or year/month selector.
- Entry source: All, Manual, Auto, TMS, Cash Reports, or other existing source values.
- Voucher number or description search.
- Optional account filter.

Filtering will be performed in the database query, not only in the browser, so the list remains usable with large datasets.

### 6.5 Journal detail

Selecting a journal will show a detailed, balanced voucher with:

- Company header.
- Voucher number.
- Branch.
- Entry date.
- Description and reference.
- All debit and credit lines.
- Account type and account name.
- Line descriptions.
- Total debit and total credit.
- Balance confirmation.
- Source and automatic/manual status.

## 7. Excel Import and Export Plan

### 7.1 Import template

The Journal List or Create page will provide a downloadable template with two sheets:

| Sheet | Purpose |
|---|---|
| Journal Entries | One row per journal header with a shared import key. |
| Journal Lines | One row per line linked to the header import key. |

The template columns will be:

**Journal Entries:** `Import Key`, `Branch`, `Entry Date`, `Description`, `Reference`.

**Journal Lines:** `Import Key`, `Line No`, `Account`, `Debit`, `Credit`, `Line Description`.

The template will include an Instructions sheet describing branch matching, date format, account naming, debit/credit rules, and the requirement that each import key balances.

### 7.2 Import validation

Import will validate the full workbook before posting anything. It will reject the workbook if:

- A branch cannot be matched.
- An account cannot be matched within the selected branch.
- A line has both debit and credit or neither.
- A journal has fewer than two lines.
- Debit and credit totals differ.
- A duplicate import key exists.
- A date or amount is invalid.

The import process will submit balanced entries one at a time through the same server-side posting function used by manual creation. It will show row-level errors and will not silently skip invalid rows.

### 7.3 Export

The Journal List will export the filtered journal headers and lines to a workbook. The export will include:

- Journal Entries sheet.
- Journal Lines sheet.
- Summary sheet with filters and totals.
- Instructions or metadata sheet describing the export timestamp and filter scope.

## 8. PDF Export Plan

Each journal entry will have an Export PDF action. The PDF will reuse `src/lib/branded-pdf.ts` so it has the same company header and footer treatment as the existing Trip Note PDF.

The PDF will include:

- Garuda Logistics Solutions header.
- Journal Voucher title.
- Voucher number.
- Entry date.
- Branch.
- Description.
- Reference.
- Account lines with account name, account type, line description, debit, and credit.
- Total debit and total credit.
- Balance status.
- Source marker, including Automatic Opening Balance when applicable.
- Existing branded footer and page numbering.

A wide journal line table may use landscape orientation or a carefully sized portrait layout depending on the final column widths. The output filename will include the voucher number and date.

## 9. Permissions and Safety Rules

The implementation will preserve the project’s existing Accounts access guard, then add server-side checks for accounting invariants.

The following records will not be deleted directly:

- Default capital ledgers.
- Opening Balance Equity ledgers.
- System bank and cash ledgers.
- Automatic opening-balance journal entries.

If correction is needed, the system will use an update or reversal workflow rather than deleting accounting history. Manual journal edits should be restricted once the entry is posted; the safer first implementation is to support reversal and replacement rather than mutation of posted lines.

## 10. Implementation Sequence

The work will be delivered in the following order so each layer can be verified before the next one depends on it.

| Phase | Scope | Verification |
|---|---|---|
| 1 | Add migration for system capital and opening-equity accounts, constraints, indexes, provisioning, and corrected auto-opening postings. | SQL verification queries; existing bank/cash backfill remains idempotent. |
| 2 | Add balanced manual journal-posting RPC and read helpers. | Database tests for balanced, unbalanced, cross-branch, invalid-side, and duplicate/system-account cases. |
| 3 | Update Ledger UI with Capital sub-tab and remove revenue opening-balance fields. | Targeted UI checks and manual branch-by-branch behavior. |
| 4 | Add Journal route, navigation, Create tab, dynamic multi-line form, and live balance validation. | Manual create test with two and multiple lines. |
| 5 | Add Journal List, branch/month filters, detail view, and automatic-entry visibility. | Verify opening entries appear and filters return correct records. |
| 6 | Add Excel template/import/export. | Round-trip export/import test with balanced and invalid workbooks. |
| 7 | Add branded per-entry PDF export. | Open generated PDF and verify header, lines, totals, and footer. |
| 8 | Run build, targeted lint, tests, migration verification, and commit/push. | Clean diff and successful production build. |

## 11. Acceptance Criteria

The implementation will be considered complete when all of the following are true:

1. Opening the Accounts Ledger page shows Capital, Create, List, and View tabs.
2. The Capital tab shows exactly one default capital ledger for every branch.
3. A user cannot create a second capital ledger for a branch.
4. Revenue ledger creation has no opening-balance amount, date, or side field.
5. Revenue ledger creation with injected opening-balance values is rejected server-side.
6. Capital opening balances create a balanced automatic journal entry with both lines linked to real ledger accounts.
7. Bank and cash opening balances create balanced automatic journal entries with a real Opening Balance Equity offset.
8. The Journal module has Create and List sub-tabs using the exact TMS-style mobile dropdown.
9. Journal Create supports multiple debit and credit lines.
10. An unbalanced journal cannot be saved through either the UI or the database RPC.
11. A journal cannot mix accounts from different branches.
12. Automatic opening entries appear in the Journal List and are labeled as automatic.
13. Journal List filters by branch and month and shows correct totals.
14. Excel import validates the complete workbook before posting entries.
15. Excel export includes headers, lines, and filter metadata.
16. Each journal entry exports as a branded PDF with voucher details and balanced totals.
17. Existing Accounts Master, Ledger, TMS, and unrelated application behavior remains intact.

## 12. Assumptions Requiring Confirmation During Implementation

The plan uses the following reasonable accounting assumptions:

- The opposite side for opening balances is a real branch-level `Opening Balance Equity` ledger.
- One capital ledger is created automatically per branch and is not manually duplicated.
- Revenue ledgers may be posted in normal journals but cannot have opening balances.
- Bank and cash opening balances remain maintained in their respective Masters and are mirrored into the ledger/journal system automatically.
- Posted automatic entries are immutable; corrections use a controlled reversal or regeneration path.
- The existing branch access and AccountsAccessGuard remain the source of UI access control, while database functions enforce accounting correctness for every caller.

These assumptions can be adjusted before implementation if the business wants a different offset account name, capital account naming convention, approval workflow, or journal-edit policy.
